# Spec Pass

## Overview

The heavy-model challenge pass that turns an executor-minted stub into a plan a cheaper model can execute — or stamps that it can't be. The product is a **verdict**, not polished prose. **Mis-framing, not missing detail, is the expensive failure**: most stubs are minted mid-execution of something else by whatever model was executing, so assume framing debt.

**Shared stamp authority (plan 1373 D3).** This skill's stamp step (step 4 below) is the single
authority for `stage`/`execModel`/`specReview` verdicts — `board-pass` Phase 2 calls the SAME authority
for any plan the operator wants re-verdicted mid-sweep, rather than re-implementing the stamp logic
itself. Standalone spec-pass survives because applying the exit test to one fresh mint, with no full
board sweep, is a real, cheap use on its own.

**Routing out of `pending-approval/` (plan 1371).** Since plan 1371, every fresh mint rests in
`pending-approval/` until this pass stamps it. When step 4 stamps `stage: specced`, that stamp is also
the plan's exit from `pending-approval/` — route it in the same pass to `ready/` (the normal case) or the
matching `waiting-{blocked,operator,date,trip}/` if the plan is blocked/gated. A plan does not stay in
`pending-approval/` once specced (the folder holds `stage: stub` only) — see the plans-workflow runbook's
folder-layout table for the full lifecycle.

Baseline evidence (2026-07-02, 2× Sonnet incl. a pressured batch-sweep run): models verify stub claims against the repo natively once a review is asked for. This skill's load-bearing content is therefore what a reviewer cannot invent — the verdict **stamps** (step 4), the **execModel litmus**, and the **cross-plan sweep** (step 5). The rest is a checklist, not a discipline lecture.

## Procedure (per plan)

> **Concurrent spec-passes are UNDETECTED — check before you fan out.** There is no per-plan lock for spec-review. Execution claims take a claim ref (`refs/heads/coord/claims/<id>` since plan 3756); a spec-pass takes nothing. `stampFrontmatterAxis` is atomic per push — on a non-ff rejection it freshens onto `origin/master`, re-reads the plan, and re-applies the stamp — but it has **no compare-and-refuse**: it never asks whether the freshened file already carries someone else's verdict, it just writes its own on top. (Contrast `edit-plan --body`, which DOES carry a stale-base fingerprint guard naming `stage`/`specReview` — the stamp path has no equivalent.) So two concurrent spec-passes cannot corrupt the file, but CAN silently overwrite each other's verdict — last writer wins, no warning. The board-wide mutex `refs/heads/coord/spec-sweep-lock` (legacy `refs/coord/spec-sweep-lock` dual-read; `scripts/spec-sweep-lock.mjs`) was, until 2026-09-13, wired only by the scheduled cloud spec-sweep routine and board-pass's own `pending-approval/` phase — added after the 2026-07-20 collision, a ~370k-token 5-verifier fan-out that turned out to be pure confirmation of what the routine had stamped minutes earlier. A standalone `/spec-pass` did NOT take it, and on 2026-09-13 the same shape recurred: a local `/spec-pass` on five fresh stubs found the lock held by the cloud routine, waited for the release before writing anything (so no verdict was overwritten), but had already fanned out five verifiers in parallel with the routine's own reads — the lock stopped the writes, not the duplicated work.
>
> **The rule (operator ruling 2026-09-13, paraphrased: every spec-pass takes the lock before it starts reading, a single plan included): `node scripts/spec-sweep-lock.mjs acquire` is the FIRST action of any spec-pass, before the plan body is read and before any verifier is dispatched.** If the lock is held, wait for its release (poll `node scripts/spec-sweep-lock.mjs status`) and then re-read the plan's frontmatter from `origin/master` — a `specReview` sha that appeared while you waited means the other pass got there first: take its verdict, and re-challenge only where you have a concrete reason (a wrong file, a task already shipped, a weakened decision), never as a routine second opinion. Release with `node scripts/spec-sweep-lock.mjs release` when the last stamp is pushed. The pre-ruling convention (single plan reads freely, only multi-plan sweeps hold the lock) is retired: it de-duplicated writes but not reads, and reads are where the tokens go. A per-plan lock needs no new primitive if it is ever wanted — `acquireLock` already takes a `ref` override, so `--ref refs/heads/coord/spec-review-<id>` (via `coord-refs.mjs`'s `coordRef()`, per plan 3756) reuses the same CAS and stale-takeover semantics. **A hidden or lost acquire result is re-checked with `status`, and a `won:false` immediately after your OWN acquire is answered by re-running `acquire`** (idempotent since plan 4083 — a live lock whose token is your own wins instead of reading as a sibling), never by assuming a sibling and walking away holding the lock for the rest of the TTL.

1. **Verify load-bearing claims against the repo** (absorbed from the retired challenge-plan skill, 2026-07-04 — a check without pasted evidence, command output or file:line, did not happen; if the project keeps a subject wiki, read the plan's subject page IN FULL first and name it in the verdict):

   | --- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | C1  | Premises still true    | Extract the plan's factual claims — files, symbols, line refs, "X is not yet done", AND the semantic assertions attached to them — verify each at its cited location against fetched `origin/master`. Matching the quoted value at the quoted line is HALF a check; the sentence around it is a premise too. A plan with a `program:` tag or a child-N-of-M Status line carries a `## Inherited premises` section; verify each line exactly like the plan's own claims, and fail the pass if the section is missing while the parent carries `## Proven mechanisms` |

   Correct the body in place. A confidently wrong stub survives prose review; it does not survive an open file.

   **`program:` siblings (plan 1840).** If the stub carries a `program: <slug>` frontmatter tag, pull up
   the other plans sharing that value (active AND archived) before finishing C1–C3 — they are the same
   multi-plan mission, so their outcome, prior hypotheses, and archived rationale are load-bearing
   context for this stub's own framing, not just background reading.

   **Inherited premises (plan 3943).** A program child assumes mechanisms it never states — it assumes
   them BECAUSE THE PROGRAM assumed them — so C1, which reads only the plan's own cited claims, never
   sees them. Write them down: the child carries a `## Inherited premises` section, one line per
   mechanism, each naming where in the code it can be verified; the parent program keeps the same list
   under `## Proven mechanisms`, each line naming the plan or commit that proved it. Archiving a parent
   does not delete its premises — the child COPIES them at mint time (the re-spec sitting that mints
   children writes them), so the list survives the parent. `lint-plan-index.mjs` enforces the section's
   presence for a `program:` child in `ready/`; the child-N-of-M prose form is yours to catch, since a
   lint cannot key on a free-prose Status line. Motivating case: plan 3858 passed a real spec-pass (53
   cited steps verified, three premises corrected) and still missed the fatal one — an apply-side hold
   never reaches a judge in any pass, an assumption of the archived parent 3796, which cost 405 correct
   prices on 189 clinics and an operator ruling.

2. **Challenge the framing.** What else explains the symptom? Is this a row-level patch where a structural fix is due? Does an existing plan/runbook already decide this? (Re-challenge mode: the same pass can be re-run on an already-`specced` plan on suspicion or staleness — it may downgrade the plan to stub or flag it as a close candidate.)
3. **Write acceptance criteria** precise enough that a cheaper executor cannot drift: verifiable outcomes, not activities.
   3b. **Make the front-loadable calls NOW — the exit test (operator 2026-07-03).** Ask: "could a Sonnet session execute this without making a judgment call on a correctness-critical surface?" If no but the calls can be made at spec time, make them, as an `## Execution notes for the drain` section pinning (a) **placement** — where in the existing flow each change goes (the classic slip: correct code outside a retry/mutate seam), (b) the **failure modes** that placement avoids, (c) a **do-not-touch** list, (d) a **test-harness pointer**. Stamp `sonnet` only when the answer is yes. Contract + worked example (plan 1362 E1–E5): the project `docs/runbooks/plans-workflow.md` § "Spec-pass exit test". If a front-loadable call needs OPERATOR judgment (not repo facts) and the operator is in-session, asking is MANDATORY, not optional: extract it now with a `/grilling`-style micro-interview — group a plan's open questions into ONE question set (each question carrying a recommended answer) rather than many single-question round trips — and pin the answers in the Execution notes. Never route a plan to `waiting-operator/` without having asked first; that park is ONLY for when the operator is absent or explicitly defers.
   **The carrier question (plan 3943).** The exit test gains one more question, asked whenever a plan
   moves a decision OUT of deterministic code or out of a prompt and INTO a judge seat: **which seat
   receives the undecided value, and in which pass does a judge sentence it?** Verify the answer, never
   assert it, against three things: the **wire schemas** (can the field be absent — an extractor/shaper
   enum with no null member cannot carry "undecided"), the **merge-blocking set** (`assembly.py` — does
   leaving the axis unset fuse two real rows), and the **phase order** in `run-batch.py` (does a hold at
   that stage actually reach `_update_oracle_held_rows`, or is it stamped after the judge seat has
   already run). A plan that cannot answer is not a hold plan: it is a code-first plan or a keep, and
   the pass says which. Plan 3941's T0/T0b tables are the worked example and the first data. Motivating
   case: plan 3865 rewrote 23 prompt rules to "capture the construct, leave the axis for the judges" and
   all 23 were reverted, because `pricing_mode`, `service`, `time_window` and `home_visit.offering` are
   required closed enums with no null member. Its executor's own closing line: establish that the axis
   can carry "undecided" end to end BEFORE moving the decision.
   **Grill-escalation triggers (operator 2026-07-16, seventeenth board-pass).** Upgrade the one-shot grouped question set to a full `/grilling` interview (one question at a time, each with a recommended answer, every resolved answer folded into the plan body as you go) when ANY of these holds:
   - **(a) Verification REFUTES a load-bearing premise that came from the operator's own observation.** The stub's frame may encode a misunderstanding only an interview can surface — no repo check reaches it. Evidence: plan 1905 — the operator believed AniCura published an akut time band; that belief surfaced (and reversed the design) at interview question 3, after every file:line premise check had already run.
   - **(b) The verdict pins USER-FACING claim semantics** — labels, time spans, suppression rules, anything where the surface asserts a fact to users — and the plausible recommended default would assert something we cannot verify. Evidence: 1905 again — clipping window ends to Google-Places hours looked reasonable and was wrong; the interview produced the safer open-start "efter X" scheme.
   - **(c) The operator asks for it** (any "grill me" phrasing).
     Cost is a few extra question turns; skipping it on a trigger-(a)/(b) plan risks stamping a spec that ships a confident wrong default (the 1905 pre-grill spec would have).
     **Sessions decide tech-design and scope forks themselves — only the fixed operator-axis list may still park (operator ruling 2026-09-20, plan 4069).** Before writing anything into `## Grill questions`, ask whether the question is actually a technical-design choice or plan-scope bureaucracy (split / fold / which lane / which model / file a follow-up or not) — the operator does not want those brought to them. Pick the recommended option, write it under a `## Session decisions` section in the plan body (the option chosen, one line why), and proceed; never park it. A question survives to `## Grill questions` only when it names one of: `product` (what users see), `policy` (a rule/default for a repeated ambiguity, a taxonomy boundary, legal/privacy posture), `money` (cash above the drain's spend ceiling), `access` (credentials/accounts/dashboards/a physical operator action), or `data-ruling` (a seed-row edit under the hand-edit ban, a dossier sign-off) — tag it accordingly, e.g. ``1. `[axis: policy]` **Which default applies?**`` (`move-plan.mjs`'s entry gate fail-refuses an untagged or unrecognised-tag question). Bundle a single genuine taste/policy question together with its session-decidable sub-questions as ONE parked question, answering the sub-questions yourself.

     **Park-don't-ask when the operator is NOT in-session, or when this pass is one plan in a sweep (plan 2034).** The "asking is MANDATORY" rule above governs the in-session, single-plan case for a genuinely operator-only (axis-tagged) question. Inside an autonomous or batched pass it inverts: **never ask inline** — a 10-plan board-pass must not block on question one. Write the open questions into a `## Grill questions` section instead — since plan 4069 session decision S1, a NUMBERED LIST ONLY: each item opens with `N. ` immediately followed by its `[axis: <tag>]` marker, and the context-to-answer-cold plus your recommended answer goes INDENTED underneath that same item (you have full context loaded now and will not weeks later) — nothing else (a bullet, a bold line, a bare unindented sentence) belongs in the section. Then `node scripts/move-plan.mjs <id> waiting-grill` and move to the next plan. `--blocked-by` is optional for that lane; the entry guard requires the questions section to be non-empty, numbered-list-shaped, AND every item tagged. The operator empties the lane in a batched `/grill-lane` sitting, which records `## Operator rulings` and routes each plan out. Choosing between the lanes (R1): a reply that is a go/no-go on an already-specified action → `waiting-operator/` (`--blocked-by` carrying one `[axis: <tag>]` from `product|policy|money|access|data-ruling|hold`); a reply that is _content_ which must land in the body before execution can be specified, and fits one of the axes above → `waiting-grill/`. A single design fork that fits no axis is a session decision (`## Session decisions`), not a park at all.
     **Data-first operator questions are STILL front-loadable (operator directive 2026-08-01, plan 2689).** When the operator's call depends on data that does not exist yet but is a cheap READ-ONLY computation (an impact count, a corpus table, a row diff), compute it IN THIS PASS — inline or via a read-only dispatch — then ask (in-session) or park in `waiting-grill/`/`waiting-operator/` with the computed table pasted into the question. Do NOT stamp `loop: hitl` and route to `ready/` on the reasoning "computing the input is the plan's own first work item" — that parks an un-drainable plan in the drain lane and defers a front-loadable exchange to a mid-run block (the 2689 mis-route this rule exists to kill). `hitl` is reserved for exchanges whose input genuinely depends on mid-IMPLEMENTATION state no upfront computation can produce.

4. **Stamp the verdict** in frontmatter. **The stamp refuses a body with no `## Spec-pass verdict` section (plan 3943); write the verdict BEFORE stamping, in the edit-plan step.** The section must name each check `C1`–`C5` with a `PASS`/`FAIL`/`PARTIAL` tag on its line, plus an execModel **litmus** line and an **exit test** line — `findPromotionBlockers()` checks those tokens mechanically, before anything is written, and nothing semantic. `--spec-review exempt-mechanical` is exempt (no judgment pass happened, so there is no verdict). The companion refusal is at pickup: a plan stamped `specReviewBy: undeclared` can no longer be claimed or drained, so the `--provenance` lookup below is not optional paperwork.
   - `stage: specced` + `specReview: <sha>` (pin to the sha you verified against; far drift downgrades it back to pending) + `specReviewBy: <model>/<effort>` via the stamp tool's `--provenance` flag (plan 3004) — declare the model and reasoning effort THIS session is running, from your own knowledge of your config (e.g. `fable-5/xhigh`; effort is one of `low|medium|high|xhigh|max`). It is a labeled SELF-REPORT, never harvested or inferred — and "not stated in my context" is NOT "unknowable" (operator correction 2026-08-11, plan-3118 pass): the effort tier is IN your config — read `effortLevel` from the session's own config dir `settings.json` (`$CLAUDE_CONFIG_DIR/settings.json`, e.g. `<home>\.claude-acct-b\settings.json`; the operator's statusline displays the same value, so they can confirm it live). Look it up BEFORE stamping; only if that lookup genuinely fails (or a mid-session effort override makes it uncertain — then ask the operator, who sees it in the statusline) omit the flag and let the tool stamp `specReviewBy: undeclared` rather than guessing (a wrong guess recorded as truth is the dishonesty the field exists to end). Never pass it with `--spec-review exempt-mechanical` — no judgment pass happened, so there is nothing to attribute (the tool refuses, and stamps no `specReviewBy` at all there).

     4c. **Tool ORDER for applying the verdict (the project; learned the hard way 2026-08-04, plans 2820/2821).**
     The stamp/route tools interlock — run them in exactly this order, and author the body for the
     POST-stamp state BEFORE stamping. **Since plan 3973 (T2), steps 3-5 collapse into ONE command
     and ONE master commit:**
     `node scripts/stamp-exec-model.mjs <id> <lane> --spec-review <sha> --provenance "<model>/<effort>" --cloud-exec <true|false> [--env <cloudEnv>] --move ready|<waiting-state> [--blocked-by "…"]`
     is the DEFAULT way to apply steps 3-5; the single-axis
     commands below (`stamp-cloud-exec.mjs`, `stamp-exec-model.mjs` without `--cloud-exec`/`--move`,
     `move-plan.mjs`) keep working unchanged and are the fallback when a step needs machinery the
     combined form does not carry (a `false` cloud-exec's `.claude/`/`.husky/` gate override flags,

     1. `edit-plan.mjs <id> --body <file>` — ALL body prose (rulings, execution notes, task ticks) goes
        in FIRST, while `stage:` is still `stub`. Do NOT put `stage`/`specReview`/`execModel` in this
        frontmatter — `stamp-exec-model.mjs` owns them, and the board write-gate REFUSES any edit-plan
        write that would leave a specced plan resting in `pending-approval/`. `--base-sha` is
        **REQUIRED** for `--body` (plan 3244 retired the old auto-capture) and takes a **blob** sha,
        not a commit sha: capture it AT READ TIME — `git rev-parse origin/master:<plan-path>` in the
        same breath as the `git show origin/master:<plan-path>` you authored the body from. Never
        re-run `rev-parse` just before the edit; a fresh sha recreates the exact blind spot the
        auto-capture had. Omitting the flag exits 2 with a teaching message.
     2. Body-authoring rules the LATER steps depend on (add these to check C5): the `**Status:**` line
        must not lead with the token `STUB` (the plan-2587 prose-vs-stamp check compares it against the
        frontmatter after stamping), and the body must carry an H1 plus BOTH banners (🟥/🟩 SEED-WRITE,
        💰) — `move-plan.mjs` anchors the `**Blocked-by:**` header on the banner block and hard-fails
        without it. A mid-execution mint often lacks all three. **Since plan 2892 the TOOLING enforces
        this rather than leaving it to your care:** step 3 refuses BEFORE it writes anything when a
        banner is missing or unparseable (the plan stays `stage: stub`, so step 1 still works and the
        refusal's fix menu is executable), and it rewrites a STUB-leading `**Status:**` token to the
        specced form itself. Author the body right anyway — a refusal still costs you a round-trip.
     3. `stamp-cloud-exec.mjs <id> …` — BEFORE the exec-model stamp, while `stage:` is still `stub`
        (legal: the tool resolves plans in `pending-approval/`, `ready/`, and every `waiting-*/` lane —
        it refuses only `in-progress/`/`archive/`). Its `.claude/`-path scanner fires on prose MENTIONS
        too; a mention-only hit re-runs with `--claude-dir-ok "<why>"`. **Why this is NOT a tail step
        (2026-08-08, plans 2874/2964):** the objective promoters into `ready/` — done-worktree's
        close-out promoter and board-pass promotions — stamp NOTHING, so a verdict that routes to a
        waiting lane with the cloud stamp left "for later" surfaces in `ready/` cloud-invisible when
        its blocker lands, and nothing downstream warns. Stamping before the route means every exit
        (ready or waiting) already carries the verdict. This supersedes the old post-move step-5
        placement (the retired "2812 precedent").
     4. `stamp-exec-model.mjs <id> <fable|sonnet|sol> --spec-review <sha> --provenance "<model>/<effort>"`
        — the stamp authority: writes `stage: specced` + `specReview` + `specReviewBy` + `execModel`,
        completes the `**Status:**` prose, and does the `FABLE-`/`SOL-` filename rename in one
        hook-free push. This legitimately creates a TRANSIENT specced-in-`pending-approval/` state.
        Omitting `--provenance` WARNs and stamps `specReviewBy: undeclared` (see step 4's stamp list).
     5. `move-plan.mjs <id> ready|<waiting-state> [--blocked-by "…"]` — IMMEDIATELY after; the transient
        state is legal only between these two commands.

     **The deadlock this order avoids — now closed in the tooling (plan 2892).** Historically, once
     `stage: specced` was stamped, a body defect from step 2 (STUB-leading Status prose, or a missing
     banner) wedged BOTH tools — edit-plan refusing on specced-in-pending residency, move-plan refusing
     on the prose/anchor — with each tool's fix menu prescribing the other. It fired at least 7 times
     across 2026-07-30..08-04, and recovery was hand-rolled (BOARD_GUARD_OVERRIDE hand-move +
     `build-index.mjs` resync + a `--no-verify` push past the coord-trailer lint). Two fixes retired it:
     the stamp validates the whole promotable state before writing (step 4 above), and
     `board-write-gate.mjs` now ADMITS any write whose post-state violation set is a strict subset of
     its pre-state set — so stacked violations can be cleared one at a time, in any order, by ordinary
     `edit-plan` / `move-plan` calls. The ORDER above is still the right one to follow: it avoids the
     round-trips, and `BOARD_GUARD_OVERRIDE=1` remains the documented last resort for anything neither
     fix reaches.

5. **Batch mode only:** look ACROSS plans — folds (same files/subsystem), duplicates, contradictions, priority inversions, **and execution-batch candidates**. Apply **the share-a-land criterion** — see `batch-train/references/share-a-land.md` for the full three-outcome test and eligibility rules (2–5 members, all `stage: specced` + `execModel: sonnet`, homogeneous seed-write mutex class); don't restate it here. This cross-plan view is the one thing a just-in-time single-plan pass cannot see. (Two senses of "batch" now coexist in this skill: _this_ batch mode is spec-pass reviewing many stubs in one sweep; an _execution batch_ is plans later running together in one worktree/land via `batch-train` — don't conflate them.)

## The execModel litmus test

Can the acceptance criterion be stated precisely NOW, before contact with the data? **Yes → front-loadable.** The criterion itself gets discovered during the work → **interleaved.**

**This litmus defers to the executor-lane toggle — it does not name a lane itself.** Read `scripts/exec-model-default.json` with `node scripts/exec-model-default.mjs` before stamping. When the toggle names `sol` (restored 2026-09-03, plan 3656, reversing the 2026-09-01 suspension), elect `sol` for both branches whenever the plan is mechanical/well-mapped and not on the coord-spine hard gate below, with `sonnet`/`fable` surviving only where the pass records why Sol cannot take the plan. When the toggle names a Claude lane — `sonnet` or `fable`, and for THIS litmus the two mean the same thing, "the Claude lanes are in force" — the shape answer above picks between them: `sonnet` for front-loadable, `fable` for interleaved. `sol` is then stamped only on an explicit operator instruction for that plan, never elected by this litmus and never inferred from a plan looking Sol-shaped. (The toggle's exact Claude value is not wasted: it is the lane the Tier-0 `exempt-mechanical` backfill writes, where there is no shape answer to consult.) The coord-spine hard gate below still forces `fable` regardless of the toggle's value. (History: from 2026-08-26 to 2026-09-01, and again from 2026-09-03, this test elects `sol` by default for both branches, plans 3461/3341/3656; from 2026-09-01 to 2026-09-03 it elected the Claude lanes instead, plan 3617. Flipping the toggle needs no edit here — that is the point of plan 3656.)

Phrases in a plan body that predict `fable`: "decide with the file open", "do not blind-fold", "needs corpus validation", "naive version proven wrong", concurrency/race semantics, large cross-cutting migration.

**Environment is still a real constraint on `sol`, whenever the operator does elect it.** Codex transport is reachable local and on full-egress cloud (`SOL_FULL_EGRESS_CLOUD_SUPPORTED`, clear since plan 3380); trusted/limited-egress cloud has no route to `api.openai.com` and is a permanent refusal — a plan confined to that environment cannot be `sol` at all, so record `sonnet` with that reason. The coord-spine hard gate below is the other standing exclusion.

**Whether batch candidacy is a tiebreaker follows the toggle.** `batch-train` requires `execModel: sonnet` on every member (share-a-land, step 5 below). When `scripts/exec-model-default.json` names a Claude lane, `sonnet` is already the front-loadable default, so batch candidacy doesn't decide anything on its own — it only matters in the other direction: a plan the operator has explicitly elected for `sol` cannot also ride a train, so if this pass has actually identified it as sharing a land with others (via the cross-plan sweep or an existing batch-roster entry, never a guess that a batch might show up later), say so and let the operator choose between the Sol election and the train. When the toggle names `sol` instead, batch candidacy is a real tiebreaker: a plan this pass has actually identified as sharing a land with others stays `sonnet` for that recorded reason, overriding the toggle's Sol election. Record **batch candidacy** as the reason whenever it is what settled the lane.

**Hard gate — coord mutex/write-spine surfaces (plan 1704).** A plan whose steps touch the project's coord lock or write-spine scripts (the project: `scripts/landing-lock.mjs`, `scripts/battery-lock.mjs`, `scripts/coord/excl-lock.mjs`, `scripts/coord-edit.mjs` — or extract/move their logic) is NEVER stamped `execModel: sonnet`, regardless of how mechanical the diff looks or how precisely the acceptance criterion can be stated. Evidence: plan 1678 passed the litmus (criterion statable, all car gates green) and still cost the coord-spine5 train four review-fix rounds on lock failure semantics — on these surfaces the load-bearing judgment arrives with the review findings, after execution, where the litmus cannot see it. Stamp `execModel: fable` (thin-orchestrator at execution, on the lane's default Opus 5 executor — the old "Opus after the Fable window" wording is retired, plan 2345).

## Escalation — when a stub is superpowers-worthy (do NOT stamp)

This pass is the default for every stub; the full superpowers ceremony (brainstorming → writing-plans) is the exception. The discriminator is **who is the oracle for what's still open**:

| Oracle for the open questions                                                                                                             | Verdict                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The repo — premises, placement, existing patterns                                                                                         | Verify + stamp (steps 1–4 as usual)                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Execution contact — the criterion's details get discovered in the work                                                                    | Stamp `fable`: settled frame, interleaved judgment                                                                                                                                                                                                                                                                                                                                                                                                                    |
| The operator, 1–2 bounded calls                                                                                                           | Step 3b micro-interview, then stamp                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| The operator, entangled intent / architecture / product-shape questions — or the stub is an epic needing decomposition into several plans | **No stamp.** Leave `stage: stub`, route to `waiting-operator/` with an `unblock:` marker naming a brainstorming session                                                                                                                                                                                                                                                                                                                                              |
| Nobody yet — the question itself can't be phrased precisely (not merely blocked: genuinely un-phrasable until something else is learned)  | **No stamp. Demote to fog** (plan 1668): append the underlying question as a patch to `docs/superpowers/plans/FOG.md` § "Not yet specified" (via `coord-edit.mjs`), then archive the stub and flip its stamped status to `🌫️ DEMOTED TO FOG — see FOG.md` (`move-plan <id> archive` + `edit-plan.mjs`, the fold-procedure step-4 pattern). Don't pre-slice the fog patch to mirror the stub's structure — board-pass's fog sweep decides what it graduates into later |

Secondary escalators — any one bumps a clean-looking stub up a rung: a one-way door (new schema axis, data-model change, public URL structure), a new subsystem or cross-cutting migration, visual/UX shape questions. The in-pass tell: step 2's framing challenge stops feeling like _verifying_ and starts feeling like _designing_ — the moment you are inventing the design rather than checking it, stop stamping and escalate. Full three-line triage gate: the `plan-triage` skill.

## Common mistakes

- Polishing prose instead of verifying claims — the exact failure mode this pass exists to catch.
- Reviewing the plan _text_ only; the pass is worthless without the repo open.
- Stamping `sonnet` because the plan is _detailed_ — detail ≠ front-loaded judgment.
- Stamping `fable` on a stub whose open questions are operator-intent or design-shape — `fable` means judgment interleaved with _execution_, not unresolved design; that stub escalates (see Escalation above).
- Doing per-plan passes when ≥5 stubs are pending — batch it; the cross-plan folds pay for the sweep.
