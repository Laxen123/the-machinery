# /gpt-review

Run a code review whose finders and verifiers execute as `codex exec` subprocesses on **gpt-6-luna** (effort high), escalating any REFUTED-or-failed (file,line) group to **gpt-6-sol** (effort high) — role parity with `/sonnet-review`'s Opus refute-adjudicator, at roughly 1/10th the token price, billed against the ChatGPT/Codex subscription rather than Claude quota. This is the **default review lane for LOCAL sessions** (plan 2663, operator 2026-07-31) **and for FULL-EGRESS cloud envs** (plan 2665, operator GO 2026-08-03): the runner self-bootstraps codex in a cloud sandbox from the configured codex-auth env secret (`coord.config.json`'s `codexAuthEnvVar`) (installs `@openai/codex`, decodes `~/.codex/auth.json` — never echo or log that secret's value). Trusted/limited-egress cloud envs still use `/sonnet-review` directly (no egress to api.openai.com, so codex cannot run there).

Evidence basis: `output/reports/gpt56terra-finder-bakeoff-2026-07-30/verdict.md` + wiki `concepts/bake-offs.md` entry `codereview-finder-gpt56terra-2026-07-30` — Luna finders (effort high) hit 17/21 across 7 frozen bake-off cases, strictly dominate Terra, and beat the Sonnet-5 baseline 8/12 vs 6/12; the two data-grounding angles (`guard-fires` + `writer-trace`) close Luna's one blind spot to Sonnet parity; Sol tied Opus-5 10/10 on the frozen adjudication replay.

**Claude data-grounding hybrid arm (plan 2766, default ON).** A real end-to-end replay of the shipped lane against a frozen "data-grounding" bug case (`output/reports/2766-c3-shipped-lane-replay/verdict.md`) found the shipped `guard-fires`/`writer-trace` codex angles did NOT reproduce their isolated 4/6 measurement (0/6-1/6 in-spine). Sonnet-5 is measurably better on exactly this class (wiki `concepts/bake-offs.md` entry `codereview-finder-gpt56terra-2026-07-30`), so ONE `claude -p --model sonnet --effort high` call runs beside the 11 codex finders, covering both data-grounding mandates in a single dispatch; its candidates join the SAME verify stage as codex candidates (tagged `finder:claude-data-grounding` — namespace-distinct from the codex `guard-fires`/`writer-trace` tags it overlaps in mandate, so resume never conflates the two transports). It bills **Claude quota, not the codex subscription** — tracked as its own token bucket, never summed into the codex total (different subscriptions, not the same currency). Pass `--no-claude-arm` to disable it (e.g. for an A/B replay measuring the codex-only lane). Unlike a codex finder failure (fatal — an angle at zero coverage exits 2), a Claude-arm transport failure **SOFT-FAILS**: the review continues on codex-only coverage (the pre-2766 status quo), and the degradation is named in `<out>/stats.json`'s `claudeArm.status` field (`'ok'` / `'disabled'` / `'not-run'` / `'failed: <reason>'`) and in `<out>/summary.md`'s "Claude data-grounding arm" section — never silent. The call adds `--settings '{"disableAllHooks":true}'` — this repo's established defense (`backend/scripts/lib/claude_hooks.py`'s `DISABLE_HOOKS_ARGS`, already used by ~15 production extraction arms) against a hook reopening the turn and appending an epilogue that becomes the reported `result` under `--output-format json` (the incident that forced this design: a Stop hook, `wiki-loaders-stop.mjs`, reopened the turn and its "📎 reconciled — no corrections" one-liner silently replaced the real answer). The call runs with cwd set to a FRESH, DISPOSABLE scratch directory outside the repo (`lib_claude_transport.run_claude_p`'s neutral-tempdir option, not repo cwd) — a real run showed `--allowedTools "Bash(git show:*)"` is a command-PREFIX match, not a sandbox, so a `git show <ref>:<path> > file.json` redirect still writes even with no Write/Edit tool ever invoked (the arm wrote a 34MB copy of the RETIRED `seed-clinics.json` monolith straight into the worktree root on a real run); the scratch cwd contains whatever the model writes so it never lands in the worktree. `--add-dir <repoRoot>` restores Read/Grep/Glob access to the real repo, and the git allowlist patterns/prompt both use `git -C <repoRoot> <subcommand>` since the scratch cwd isn't a git repo at all. As a cheap secondary layer, the prompt still asks the model to wrap its JSON answer in a `<<<GPT_REVIEW_CANDIDATES>>>...<<<END_GPT_REVIEW_CANDIDATES>>>` delimiter pair, which the parser prefers when present — this tolerates incidental prose around the JSON within the one `result` string, though it cannot recover an answer a reopened turn has structurally replaced (that is `disableAllHooks`'s job alone). `--max-turns 40` bounds a runaway agentic loop — this repo's established mechanism too (`lib_claude_transport.run_claude_p`'s `max_turns` parameter; the flag is real on the installed CLI despite being undocumented in `--help`). The value is measured, not conventional: the six recorded armed runs finished in 14-38 turns, and an earlier cap of 25 destroyed two measurement runs by capping the arm mid-answer. A cap that fires is reported as `failed: terminal subtype error_max_turns`, so an exhausted budget is never mistaken for a malformed answer. `<out>/stats.json`'s `claudeArm` object also carries `costUsd`/`turns` from the envelope — present even on a failed run, since a call can burn real spend before its answer is lost.

User invocation: `$ARGUMENTS`

Argument shape: `[--range <git range>] [--end-ref <ref>] [--concurrency N] [--out <dir>] [--repo <path>] [--no-claude-arm] [--no-gate-prep]` — all optional. **`--repo <path>` names the checkout to review** (plan 3193); without it the cwd's repo is used. Use it whenever the branch under review lives in a worktree this session is not sitting in — it is the supported way to review a worktree without a `cd`, which a Windows Git-Bash session cannot open a command with anyway (see the operator's global CLAUDE.md). `--range` defaults to `origin/master...HEAD` of the current repo. `--end-ref <ref>` marks the range as a HISTORICAL commit (the finders read via `git show <ref>:<path>` instead of the working tree, which may carry later fixes) — use it only when reviewing a frozen/past commit range, not the live branch diff. `--concurrency` defaults to the finder-angle count (11 today) so the finder phase runs as one wave. `--out` defaults to `.scratch/gpt-review/<timestamp>` under the current working directory. `--no-claude-arm` disables the Claude data-grounding arm above (default: enabled). A local worktree-branch review launch fires a detached `done-worktree <slug> --prep --no-rebase` so the heavy land gates are already proven when the review's fix lands; pass `--no-gate-prep` to opt out (plan 3503).

## What to do

1. Run the runner directly — it is a plain Node CLI (no Workflow tool needed, so a dispatched subagent can run this itself, unlike `/sonnet-review`):
   ```bash
   node scripts/gpt-review.mjs --range "origin/master...HEAD" --out .scratch/gpt-review/<slug-or-timestamp>
   ```
   Pass through whatever `$ARGUMENTS` specified (a narrower `--range`, an `--end-ref` for a historical replay, etc.). Every codex call pins `-c model_reasoning_effort="high"` — codex silently defaults to MEDIUM when that flag is omitted, so never drop it.
2. **Exit code 0** — the run completed (with or without findings; findings are the point, not a failure). Read `<out>/findings.json` and `<out>/summary.md`.
   **Exit code 2** — the review cannot be trusted. Two causes, told apart by the error text: (a) codex itself unusable (binary unresolved, or the very first call spawn-failed) → fall back to `/sonnet-review`; (b) one or more FINDER calls failed (timeout / transient transport blip) — an angle with zero coverage must not read as a clean angle, so the runner refuses to report. For (b), re-run ONCE with the same `--out` (errored calls are never checkpointed as final, so only the failed calls re-run); if it exits 2 again, fall back to `/sonnet-review`.
   **Exit code 3** — the range resolved to ZERO changed files, so nothing was reviewed. This is a HARD FAILURE, never a PASS: it leaves no `stats.json` in `<out>` — none is written, and a stale one an earlier run left in the same (slug-keyed) `--out` directory is deleted, along with that run's `checkpoint.json` + `raw/` so a corrected re-run cannot resume another range's cached answers — so the run cannot be recorded. Almost always the wrong checkout — the review was launched from the main tree (which sits on `master`) while the diff lives on a worktree branch. The error names the worktrees that DO carry commits ahead of `origin/master` and prints a ready-to-run `--repo` command for the first-ranked one (ranking is by commits-ahead only, so substitute your own path if that is not your branch). (The one legitimate empty case — every changed file is an excluded data artifact — stays exit 0 and says so.)
3. Present the result like a `/code-review` report: lead with the one-line summary from `summary.md` (files changed, candidates surfaced, findings kept), then list findings most-severe first with `file:line`, the verdict (`CONFIRMED` / `PLAUSIBLE` / `UNVERIFIED` — `UNVERIFIED` means both the Luna verifier AND the Sol escalation failed on that group; it was kept rather than silently dropped, so treat it as worth a manual look), and the failure scenario. If `findings.json` is `[]`, say so plainly.
4. This command does NOT auto-record the land-gate review marker. The gate (`done-worktree` REVIEW_NEEDED → `record-review.mjs`) is command-agnostic — it keys on a recorded `Review: <VERDICT> @ <sha>` marker, not on which command produced it.
5. **Record the verdict, its provenance, AND the fan-out counts.** The runner writes `<out>/stats.json` in the `--review-stats` shape (`stats.finders` / `verifierAgents` / `escalated` → `f=`/`v=`/`adj=` in the marker). `findings.json` empty → clean:
   ```bash
   node scripts/record-review.mjs PASS --review-method gpt-review --review-stats <out>/stats.json
   ```
   `findings.json` non-empty → persist and disposition, same as `/sonnet-review` (see `.claude/commands/sonnet-review.md` step 5 for the full disposition flow — `--batch`, per-key `--fixed`/`--plan`/`--wontfix`). Pick the verdict by severity (`BUGS-FOUND` if any `CONFIRMED` correctness finding, else `NITS`):
   ```bash
   node scripts/record-review.mjs <NITS|BUGS-FOUND> --findings <out>/findings.json --review-method gpt-review --review-stats <out>/stats.json
   ```
   Then disposition every finding before landing (the `FINDINGS_OPEN` gate blocks otherwise):
   ```bash
   node scripts/record-review.mjs disposition <key…> --fixed   # or --plan <id> / --wontfix "<reason>"
   ```

## Fallback rule

If the runner exits 2 for a codex-transport failure (not found, not authenticated, or the first call couldn't even spawn), do not loop retrying it. Say so plainly and run `/sonnet-review high` instead for this review round. (A finder-failure exit 2 gets ONE same-`--out` resume first — see step 2.) Record whichever lane actually ran; never record `gpt-review` provenance for a review `/sonnet-review` produced, or vice versa.

## Subagent note

A dispatched subagent (thin-orchestrator lanes, `execModel` drains, `/orchestrate` / `/local-drain` workers) has NO Workflow tool, so it cannot run `/sonnet-review` or the built-in `/code-review` — but `/gpt-review` is a plain CLI, so a subagent CAN run the real fan-out itself (finders + verify + escalate), not just a single-agent substitute. Record `--review-method gpt-review` in that case — it is a legitimate, non-downgraded provenance from a subagent, unlike `substitute`. See `the project/CLAUDE.md` § Review calibration and `docs/runbooks/review-calibration.md`.
